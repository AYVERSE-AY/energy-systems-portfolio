# 技术项目报告规范

适用于本仓库所有 `projects/NN-*/REPORT.md`。目标不是让文档看起来学术，而是让结论
可追溯、有边界、可复现。

## 1. 章节结构

按顺序，缺项可省略但要写明原因：

1. 项目摘要（对象 / 目标 / 方法 / 主要结果 / 适用范围）
2. 研究背景与分析目标（要回答的具体问题，3–5 条）
3. 测试系统与建模条件（数据来源、设备数量、求解参数、判据）
4. 计算方法与结果判定（流程、指标、有效性判据、异常处理）
5. 基准结果
6. 主要计算结果（表格 + 图）
7. 结果分析与技术讨论（现象 / 解释 / 适用边界分开写）
8. 结论（逐条对应目标与证据）
9. 研究局限
10. 可复现性说明（环境、命令、输入、输出、复核方式）

## 2. 三个概念必须分开

| 概念 | 回答的问题 | 常见错误 |
|---|---|---|
| 求解收敛性 | 方程是否解出 | 用 `converged` 证明结果有效 |
| 结果有效性 | 结果是否覆盖被分析对象 | 把缺失值当 0，或把部分覆盖当全网 |
| 约束符合性 | 有效结果是否满足判据 | 用不符合判据的场景反推「不安全」 |

## 3. 数据可追溯

- 报告中每个关键数字必须来自仓库内的输出文件（`data/*.csv`、`data/*.json`）或
  脚本运行输出，并在文中注明文件；
- 缺失 / 无效结果留空或显式标注，禁止填 0 后参与统计；
- 统计口径（按母线、按线路、按场景）在表头或注释中说明；
- 修改脚本后必须重跑并更新数据文件，禁止为了与旧结论一致而改动原始数据。

## 4. 判据与结论

- 电压、负载率等阈值须注明是「项目自设分析阈值」还是引用标准，并给出来源；
- 结论与判据绑定表述（「在所设 0.90–1.10 p.u. 判据下……」）；
- 标准算例的结果不得推广为真实系统结论。

## 5. 区分事实、解释与假设

- 事实：由输出文件直接支持；
- 解释：基于拓扑、物理约束的合理推断，需说明依据；
- 假设：未验证的机理，必须明确标注「尚需进一步计算验证」。

## 6. 编号、符号与图表

- 元件编号规则在方法章节声明一次，全文统一（如线路用 0-based 索引、母线用 1–9）；
- 图表内的编号与正文表格一致，坐标轴单位写清（p.u.、%）；
- 图必须由仓库内脚本生成，脚本路径与输出路径使用仓库相对路径；
- 图注说明筛选规则（如「仅含全网有效场景」）与标记含义。

## 7. 可复现性

- 命令必须与仓库目录结构一致，使用相对路径，不写个人绝对路径或机器专属配置；
- 依赖版本写入 `requirements.txt`，并在报告中注明实测版本；
- 提供复核方式：重跑后 `git diff` 是否为空、行数与关键字段是否匹配。

## 8. 求职材料分离

- `REPORT.md` 只保留技术内容，不写简历 bullet、面试回答、自我评价；
- 简历与面试材料放 `CAREER_NOTES.md`，其中的数字必须与报告一致；
- 未完成的工作只能出现在「后续计划」，不得写成已有成果。

## 9. 交付前检查

- [ ] 无绝对路径、无个人用户名、无临时目录
- [ ] 每个数字能指到具体文件
- [ ] 状态分类覆盖全部场景，无「未知」被算成「正常」
- [ ] 图由脚本生成且与表格一致
- [ ] 复现命令执行成功
- [ ] `git diff` 只含本次相关改动
